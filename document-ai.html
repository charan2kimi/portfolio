Enterprise Document AI and Agent Platform

Container-level view: the infrastructure an enterprise AI product ships on. The platform began as a private chat and document chat service, private and public models behind guardrails, with de-identification whenever a public model is involved, streaming answers to users. It grew into the document AI pipeline and the agent harness that analyst and data science teams run their work through today. Deployed in customers' own environments for regulated healthcare, financial services, and public sector work. Architecture

Six planes. Every request passes the safety plane first; documents flow through the document AI plane into retrieval; agents run inside the harness under policy; every answer comes through one serving layer; and the evaluation plane decides what ships and watches what shipped.

One document, one question, one agent run

  1. A document lands. The upload is acknowledged at once and a job goes onto the ingestion stream; the user sees status change phase by phase.
  2. The right extraction path runs. Fast text for a digital PDF, OCR with table layout for a scan, vision-language deep transformation where a model has to read the page. Chunks get self-hosted embeddings and PII and PHI tags, then land in OpenSearch.
  3. A question arrives. Five guardrail checks and prompt-injection detection run concurrently before retrieval or any agent is chosen.
  4. Retrieval, then the boundary. Hybrid BM25 plus kNN retrieval with reciprocal rank fusion pulls the evidence. If the user's policy points at a public model, names, addresses, and health identifiers are replaced from the entity maps; a private model sees the originals.
  5. The answer streams. The gateway routes the call under the user group's policy, the model streams, and the answer is re-identified on the way back to the user.
  6. An agent run starts. The harness plans, calls nested sub-agents as tools, and discovers MCP tools scoped to the namespaces the query needs, each call authorized per identity, with data access and egress decided by attribute-based rules at runtime.
  7. Code runs in the sandbox. The restricted interpreter enforces AST validation, import allowlists, and resource limits on every step, inside a microVM where the agent's designer chose one.
  8. Live or durable. Interactive runs stream; long runs execute in the background with every completed step checkpointed, so a crash resumes instead of restarting.
  9. The trace lands and production is sampled. Every run can be walked step by step in MLflow; online evals sample runs, score them with an LLM judge, and flag failures for review.

Key decisions

Three extraction paths, not one OCR pass

Decision: route each document to fast text, OCR with table layout, or vision-language deep transformation, and pick the production model for the deep path by benchmarking frontier against open-weight VL models on a 685-fact ground truth.

Alternative considered: one extraction strategy for every document, tuned until it was good enough.

Consequence: fact-level accuracy on 50,000 insurance and Medicare documents a month went from 63.3% to 97%, most of it from reworking the pipeline rather than swapping a model, and the ground truth is what makes every later model change measurable.

De-identify at the boundary, let the firm choose the model

Decision: tag names, addresses, and health identifiers at ingestion and rewrite them only when a policy points at a public model, restoring them in the answer. Private, self-hosted models see the originals.

Alternative considered: private models only, or public models with a blanket redaction that never comes back.

Consequence: at answer time a regulated firm can use a frontier model with only de-identified text leaving the deployment, or stay fully private, with the same product and the same audit trail either way. On the deep extraction path, whether a frontier or a self-hosted VL model reads the page is the same firm-level policy.

One sandbox path from test to production

Decision: the restricted interpreter that enforces AST validation, import allowlists, and resource limits is the same one an analyst tests against before publishing and the one production runs on; microVM isolation is chosen per agent by its designer, on top of it.

Alternative considered: a permissive test sandbox and a locked-down production one, or an engineer reviewing every analyst change.

Consequence: what passed in testing is what runs, analyst-authored agents reach production without a review queue, and agents that need hardware isolation get it without a second code path.

Gate before release, sample after

Decision: golden datasets are the regression gate every agent must hold before release; online evals sample production runs and score them with an LLM judge afterward; model releases get their own scoring lanes before an A/B and a phased rollout.

Alternative considered: one evaluation loop doing all three jobs, or release on demo.

Consequence: the gate is cheap to rerun and reproducible, drift the golden set never contained still surfaces in production, and a new frontier or open-weight model earns its place on the same tasks the last one did.

The three layers

Data layer

Users, policies, documents, and conversations in a relational store; chunks, vectors, and entity spans in OpenSearch; uploads and chunk files on local storage inside the deployment. Embeddings and entity tagging run on self-hosted models. Whether a frontier model may read a page on the deep extraction path, or receive a de-identified chunk at answer time, is the firm's policy, not a default.

Product layer

Chat, document chat, and agent chat behind one front door, with guardrails on every prompt, de-identification only when a public model is involved, and model policy per user group. Agents and tools authored in DevX publish into the harness over MCP; the same registry decides what each identity can discover and call.

Deployment layer

The product ships as a self-contained stack that customers run in their own environments, with their own search cluster and their own models on their hardware; frontier models through Bedrock only where the firm's policy allows. Open-weight models are served on vLLM across AWS, GCP, and RunPod GPU hosts behind the same gateway. HIPAA, HITRUST, and SOC 2 aligned deployments.
