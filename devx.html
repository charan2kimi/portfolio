DevX, API Catalog, Agent & Tool Authoring

Container-level view: the multi-tenant platform where a firm catalogs its APIs, authors agents and tools, and turns API operations into MCP-served agent tools. Three modules under one governance layer. An API catalog with dependency tracking. Self-serve agent and tool authoring that analysts and data scientists use to write, sandbox-test, and publish. An SDK that converts API operations into tools served over the Model Context Protocol (MCP) into the platform's agent harness. Largest deployment: 200+ engineers and 1,000+ APIs exposed as 2,500+ agent tools at one Fortune 500 firm. Jan 2022 to present.

Architecture

Three modules, then governance and publication, in lifecycle order. An API is cataloged, its operations become tools, a person composes agents over those tools, and nothing a person authors publishes into the harness until it passes its sandbox tests and carries its access rules.

One API's journey: catalog entry to governed agent tool

  1. Catalog. A firm's API lands in the catalog with its dependencies, deployment visibility, and operational metadata; every action runs as an authenticated identity.
  2. Convert. The SDK turns each operation into a typed, MCP-served tool with access rules and audit hooks attached. 1,000+ APIs became 2,500+ tools this way.
  3. Author. An analyst composes an agent over those tools in the self-serve flow, or a team writes one in code with the SDK.
  4. Test in the sandbox. The artifact runs against its tests in the restricted interpreter production uses. Passing is the precondition for publication, not a recommendation.
  5. Publish on green. The passing artifact is versioned into the registry with RBAC bound: which roles can see and use it.
  6. Discover, filtered. In the harness, discovery is scoped to the namespaces a query needs and to the identities entitled to the tool; unauthorized tools are invisible before invocation is attempted.
  7. Run under ABAC. The harness executes the tool inside the agent run, deciding data access and egress per call from the caller's attributes, and writes each call into the audit trail.

Key decisions

Convert operations with an SDK, not by hand

Decision: the SDK turns API operations into MCP-served agent tools mechanically, with the same typing, access rules, and audit hooks on every one.

Alternative considered: hand-written tool wrappers behind a platform review queue, one ticket per API.

Consequence: the review queue disappeared from the publication path, and every new firm inherits the paved road instead of re-solving it.

Gated publish, not open registry

Decision: publication is a privilege the sandbox grants: an authored agent or tool reaches the registry only after its tests pass in the same restricted interpreter production runs; SDK-generated tools carry their access rules from the catalog.

Alternative considered: open publishing with post-hoc review and takedowns.

Consequence: the harness only ever executes authored artifacts that passed their tests, which is what makes analyst self-authoring safe to offer at all; the guardrail is automated, so trust does not depend on a human approval queue.

RBAC for people, ABAC for runs

Decision: two access models for two questions. Role-based access control decides which people can see and use a published agent or tool. Attribute-based access control decides, per call at runtime, what data an agent may touch and where results may go.

Alternative considered: one role model stretched to cover runtime data decisions, or a session-scoped grant trusted for the whole run.

Consequence: a misplanned or prompt-injected step hits a deny-by-default wall the moment it reaches for data or an egress outside its attributes, while the people-facing rules stay simple enough for a firm's admins to reason about.

Silo enterprise tenants, do not pool them

Decision: isolate on the silo model: each firm runs its own deployment, tenants inside it are separate domains, RBAC polices access inside each, and rollouts phase per firm as their governance requires.

Alternative considered: a pooled deployment: one shared stack for every firm with logical, row-level separation.

Consequence: cross-firm access is precluded by the deployment boundary instead of policed by application code, domains inside a firm are isolated by RBAC and domain scoping, the blast radius of any change is one firm, and regulated healthcare and financial services customers audit a boundary they can see.

The three layers

Data layer

The catalog holds each API with its operations, dependencies, deployment state, and operational metadata; the registry holds versioned agents and tools with their access rules. Both are the source of truth the SDK and the harness read, so what an agent can call is never a copy that drifts.

Product layer

Three modules a firm's teams use directly: the catalog, the self-serve authoring flow, and the SDK. Together they are the path from an API operation to an agent tool running in the platform, with the sandbox and publish gates on it wherever a person authors something.

Deployment layer

Each firm runs its own deployment, with tenants as isolated domains inside it and Okta, GitHub, or local identity integration platform-wide. Governance configuration deploys with the artifact, not as an afterthought, and the audit trail records who published, discovered, and invoked what, under which rule.
