Architecture

Five planes in lifecycle order, plus the ingestion wing that feeds retrieval and datasets. Everything a user builds passes through the same path: author, evaluate, govern, publish. Nothing skips the gates.

One tool's journey: client API to governed invocation

  1. Import or author. A client's OpenAPI specification enters the conversion pipeline, or an analyst writes a custom tool in the Monaco editor against the curated Python library allowlist.
  2. Generate. The pipeline emits a typed, MCP-compatible tool definition. 1,000+ specifications became 2,500+ tools this way, with governed self-service replacing the review queue that used to gate publication.
  3. Evaluate in sandbox. The artifact runs against its tests in isolation. EvalPlus scores code correctness, and MLflow GenAI evaluation scores agent and retrieval quality against versioned golden datasets.
  4. Bind governance. Scoped entitlements, the tenant boundary, entity-level RBAC, rate limits, and audit instrumentation (MLflow tracing, OpenSearch structured logging, OpenTelemetry) bind to the artifact itself at publish time, not to documentation about it.
  5. Publish on green. Only passing artifacts version into the live registry. Failing artifacts return to the author with replayable failure detail.
  6. Discover, filtered. Discovery is a governed operation, not a public metadata endpoint. An identity is shown only the tools its entitlements allow, so unauthorized tools are invisible before invocation is ever attempted.
  7. Invoke under policy. The Agent Execution Platform executes the tool inside agent workflows, re-authorizing the entitlement on every call and writing each one into the SOC-aligned audit trail.

Key decisions

Convert APIs by pipeline, not by hand

Decision: build an OpenAPI-to-tool pipeline so client APIs become governed MCP tools mechanically, with the same typing, entitlements, and audit hooks stamped onto every one.

Alternative considered: hand-written tool wrappers behind a platform review queue, one ticket per API.

Consequence: the review-queue bottleneck disappeared: 1,000+ API specifications became 2,500+ governed tools through one abstraction, and every new client inherits the paved road instead of re-solving it.

Gated publish, not open registry

Decision: publication is a privilege the evaluation plane grants: an artifact reaches the registry only after sandboxed tests, EvalPlus code-correctness checks, and golden-dataset evals pass.

Alternative considered: open publishing with post-hoc review and takedowns.

Consequence: the runtime only ever executes pre-tested artifacts, which is what makes analyst self-authoring safe to offer at all: the guardrail is automated, so trust does not depend on a human approval queue.

Silo enterprise tenants, do not pool them

Decision: isolate enterprise clients on the silo model: client-specific plugins, per-client deployments, and domain isolation form the tenant boundary, entity-level RBAC polices access inside it, and rollout phases per client as their governance requires.

Alternative considered: a pooled deployment: one shared stack for every tenant with logical, row-level separation.

Consequence: cross-tenant access is precluded by the deployment boundary instead of policed by application code, the blast radius of any change is one client, and regulated healthcare and financial services clients audit a boundary they can see.

The three layers

Data layer

Airflow DAGs with Spark processing steps ingest from file uploads, API streams, and queue consumers into hybrid OpenSearch indexes (BM25 lexical ranking plus kNN vector search) and versioned datasets. The same pinned dataset versions feed fine-tuning, evals, and agent use cases, so every consumer agrees on what the data was at any point in time.

Product layer

The portal is the single source of truth for the API estate: unified discovery, dependency mapping, deployment visibility, operational metadata. The authoring surfaces (pipeline conversion, Monaco self-authoring, DSPy agent composition) sit beside the evaluation and governance planes that decide what ships, so the paved road from authored to published is the only road.

Deployment layer

Multi-tenancy runs on the silo model: client-specific plugins, per-client deployments, and domain isolation give each enterprise client a dedicated tenant boundary, with Okta, GitHub, or local identity integration and entity-level permissions operating inside it. Rollouts phase per client as their compliance posture requires, and governance configuration deploys with the artifact, not as an afterthought. The SOC-aligned audit trail is the evidence it held: MLflow traces, OpenSearch structured logs, OpenTelemetry instrumentation.
